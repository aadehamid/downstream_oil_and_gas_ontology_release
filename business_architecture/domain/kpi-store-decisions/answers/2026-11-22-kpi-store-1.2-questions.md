# The owner's answers of 2026-11-22: three questions of the KPI Store 1.2 night run

The agent's update of the night run (KPI-DEC-0003) listed three questions, the first two with a recommendation. The
owner answered the first two, asked for the agent's view on the third, and then answered it. The questions are
copied here as the agent asked them, and the owner's words word for word.

## The questions

1. Should the load add comments to the client's own gold tables and metric views? My recommendation is no.
2. Should the 114 untyped property shapes be left until after 1.2? My recommendation is yes.
3. At release time, how should the version be named? `release.json` and the doc paths still say 1.1.

The context the agent gave with the first two, in its earlier updates:

- **Comments on your own gold tables and metric views.** These are outside the KPI Store's schemas, and the load's
  safety gate forbids writing outside them. So step 9 only comments the four tables the load creates. Do you want
  the client's own tables commented too?
- **114 property shapes with no datatype or class.** The spec leaves these out and lists them in the spec file under
  "left out". Covering them would mean changing the ontology-to-lpg skill. I recommend leaving them for after 1.2.

## The owner's answer to questions 1 and 2

## Question 3

The owner asked:

> what do yiu think of 3?

The agent answered, in full:

> I'd name the release KPI Store 1.2, and I'd also stop putting the version in the folder name. The first part is required, not a matter of taste, because the upgrade command depends on it.
>
> **Why the release name must change.** The client's copy says "KPI Store 1.1" in `release.json`. The upgrade command refuses a release older than the copy and changes nothing when the two versions are equal. If the 1.2 zip still says "1.1", the client's upgrade does nothing. So at the cut, the last change before shipping should set:
> - `release.json` to "KPI Store 1.2";
> - the zip's name to `kpi-store-1.2.zip`;
> - the release line that the forms and pages show.
>
> **Why the folder name should drop the version.** About 60 places in the guides and the runbook name the folder `kpi-store-1.1`, including the handout's `cd "$USERPROFILE/kpi-store-1.1"`. An upgrade keeps the client's folder where it is. Renaming it to `kpi-store-1.2` would break their paths, and every release after that would face the same problem. So:
> - The guides name the folder `kpi-store` for a new install.
> - The handout tells an upgrading reader to use the folder they already have.
> - This is a mechanical change, and the doc test checks every block it touches.
>
> **What stays "1.1":** the history. That means KPI-DEC-0001, the saved answers, the 1.1 shipping notes, and the tests that check those records.
>
> If you say yes to both parts, I'll do the version rename at the cut and the folder rename in its own PR before it. Meanwhile I'm writing KPI-DEC-0005 for your answers on questions 1 and 2.

The upgrade command and the handout that this reply names are steps 10 and 11 of KPI-DEC-0002 (Q23), on their way
into the release when the reply was written. "The 1.1 shipping notes" are the agent's words for the records of how
1.1 shipped, which this release keeps under `business_architecture/domain/kpi-store-decisions/`.

The owner's answer:

> yes to both, go ahead with 3

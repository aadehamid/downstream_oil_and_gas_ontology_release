This guide takes you from the release zip to three loaded and checked stores: Databricks, Jena Fuseki on your Windows machine, and Neo4j Enterprise. Follow it from top to bottom, one step at a time. If a KPI Store release was set up on this machine before, start at the handout's "Start here" instead (HANDOUT.md in the release's top folder): it says which part of this guide applies. Every command in it is run by the document test, except the ones the section "What ran where" lists.

One command does the work: python -m kpi_store.runner. You run it three times. The first run compares the ontology with the sandbox and stops on a report. You clear the report. The second run cuts a correction version and loads every store. The third run proves that nothing is left to change.

For every later change, use HOW-TO-UPDATE.md in the release's top folder.

Before you start#

What you need#

  • A Windows 10 or Windows 11 machine on which you may install programs.
  • The release zip, kpi-store-1.2.zip.
  • The address of the sandbox workspace, as your browser shows it when you open Databricks.
  • The ID of a SQL warehouse you may use in that workspace. The sync check reads through it.
  • The address of the Neo4j Enterprise server, your user name there and your password.
  • The database businessprocessarchitecturegraph on that server. The copy never creates a database. If it is missing, ask the server's administrator for it before you start.

The limits#

The run keeps three limits. Code enforces each one.

LimitWhat enforces it
The notebook writes only to idp_sbx.kpi_store and idp_sbx.tech_graph.kpi_store/load_databricks.py, the class Gate. Every SQL statement of the notebook passes Gate.check, which refuses a write outside the two schemas that kpi_store.toml names (write_schemas in kpi_store/settings.py). A refused statement is never sent. kpi_store/tests/test_load_databricks.py tests it.
The notebook reads only the catalogs in kpi_store.toml.The same Gate.check. It refuses a read outside read_catalogs. It also allows three system schemas, which discovery needs: system.information_schema, system.access and system.lakeflow.
The Neo4j load writes only to businessprocessarchitecturegraph.kpi_store/copy_enterprise.py. open_target opens every session on that one name, and the server must confirm the name. It refuses the system database, a missing database and an alias. check_statement refuses any statement that creates, alters or drops a database, a user or a role. decide stops when the database holds a node that does not carry the KPI Store's marks, which the paragraph below lists. kpi_store/tests/test_copy_enterprise.py tests it.

The second limit names the catalogs of the sandbox's settings: idp_sbx and synapse_dev.

The third limit has one condition. The copy judges a node by the marks on it, not by who wrote it. It has no other way: a writer's mark on every node would change the graph hash that proves the copy. OWN_RULES in kpi_store/copy_enterprise.py holds the marks for each label.

LabelA node counts as the KPI Store's when
ResourceIt has a uri, its graph starts with the address of one of this release's modules, whatever the version, and its other labels are the projection's own.
ModuleReleaseIts version_iri starts with the address of one of this release's modules.
ModuleIts uri starts with the address of one of this release's modules.
LogicalModelIts uri is under a base that this release's models use, it has only the labels that the load gives, and its slug or its models are this release's.
TechIts uri is in the technical graph's own scheme, and its other labels are classes of the technical-graph module.
EpmStoreMarker, LogicalModelMarker, TechGraphMarkerIt names this store and holds a digest.

A node that another writer made with all the marks of one row counts as the KPI Store's, and a replace deletes it. So businessprocessarchitecturegraph must be a database into which no other writer puts ontology nodes of this release's shape. Any node without these marks stops the copy.

Everything of this guide lies in your user folder, C:\Users\ and your user name. An account without administrator rights may write there, and often not at the top of C:. This guide writes %USERPROFILE% for that folder. Type %USERPROFILE% into the address bar of File Explorer to open it. A PowerShell command writes the same folder as $HOME\, as in cd $HOME\kpi-store.

Keep the release folder in Git#

Put the release folder into Git before you change anything in it. Every later change then shows against the release as shipped, and the cut tool commits and tags each correction.

  1. Open PowerShell and go to the release folder.
  2. Make the repository and commit the release as it was unpacked. The two git config lines give the commits of this folder a name. Write your own name and address in them. Leave them out if Git on this machine already knows you. 
    git init
git config user.name "KPI Store operator"
git config user.email "kpi-store-operator@example.invalid"
git add -A
git commit -m "KPI Store 1.2 as shipped"

    The last lines name the commit and count the files.

Three rules keep the folder and the zip right:

  • The runner zips what Git tracks. In a Git folder the zip holds exactly the files that Git tracks. In a plain folder, one with no .git folder, it holds every file except caches. scripts/check-git-copy.sh proves on the release that both give the same zip, and the test job runs it on Linux and on Windows.
  • Commit only the release's files and your changes to them. Keep a Python virtual environment outside the release folder. Do not run uv init there, and do not commit the project files of a tool, such as pyproject.toml, uv.lock or .python-version: they would travel in the zip. On the first real run such files were committed in the release folder, and the zip held 928 files where the release had 926.
  • Commit your changes before a run that cuts. The cut refuses a Git folder that holds a change which is not committed, and names the files.

The release brings two files for Git. .gitattributes keeps the line ends of text files the same on every system, so keep it. .gitignore leaves out what Python leaves behind, such as __pycache__ folders.

Replace the release with a newer zip#

A newer zip of the release replaces the release folder. Your settings, your jars and your virtual environment stay.

This is for a release folder that holds no change of your own. When it holds changes, such as a module or a KPI that you applied, upgrade its tools instead with python -m kpi_store.upgrade, as HOW-TO-UPDATE.md, "Upgrade the tools from a newer release", says. The upgrade keeps your changes, and a content file you never changed takes the new release's version.

  1. Rename the old release folder, for example from kpi-store to kpi-store-old. Its .git folder goes with it, and so does its history.
  2. Unpack the new zip under the old folder's name, such as %USERPROFILE%\kpi-store, as in "Unpack the release". A folder from KPI Store 1.1 is named kpi-store-1.1: keep that name.
  3. Run the Git commands of "Keep the release folder in Git" in the new folder.
  4. Leave the local folder, the virtual environment and KPI_STORE_LOCAL as they are. If the old folder held a correction that the new zip does not hold, read "The release folder" under "How to undo" first: the stores then read behind until you load them again.
  5. Run the setup check, then the run.

What Windows itself needs#

The Windows test job proved each point below on Windows Server 2025 with Python 3.12 and Java 21.

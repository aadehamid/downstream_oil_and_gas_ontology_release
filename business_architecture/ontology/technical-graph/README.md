# technical-graph: the vocabulary of what was built

The `technical-graph` module defines the kinds of thing a technical graph records about a data platform as built, and the links between them: hosts, source databases, tables, views, metric views, pipeline steps, quality checks and agents (the decision of 2026-11-02). Since 1.1.0 it also defines the jobs and pipelines that build a data object, and the link from a data object to the one it replaces on an earlier platform. It holds definitions only. The graph's nodes, row counts, refresh times and check results stay in the technical graph and its Delta copy, never in the ontology. Designed lineage stays in `data-product`; a built thing points to its design with `tg:designedAs`. Its namespace is `https://w3id.org/mpc/ontology/modules/technical-graph/`.

It answers competency questions 45 to 50 (`../competency-questions.md`, section XI): where a number comes from, whether it can be trusted today, what a change affects, whether it is built as designed, who answers for it, and which agent or report answers for a measure. Since 1.1.0 it also answers questions 56 and 57 (section XIII): which data object on an earlier platform a data object replaces, and which job or pipeline builds it. The vocabulary cannot answer them alone, so `example/example-graph.ttl`, a small example graph, is test data the regression runs them on. Live, the same queries (`../regression/queries/q45` to `q50`, `q56` and `q57`) run on the technical graph. `kpi_store/tech_graph.py`, at the top of the release, builds that graph for one environment from what the platform reports.

| File | What |
|---|---|
| `vocabulary.ttl` | 15 classes, the check-result code list and 24 properties (12 and 22 in 1.0.0). The platform layer is a value of `data-product`'s layer code list, not a list of its own. Measures are `kpi` measure definitions and systems are `system` systems, by IRI |
| `shapes.ttl` | The shapes a technical graph meets, checked with the `data-product`, `kpi` and `system` releases loaded |
| `example/example-graph.ttl` | The example: everything upstream of the metric views that compute the crack-spreads measure, with the agents, checks and steps that touch it, in the module's terms. It holds one test design so question 49 has an owner to find, and made-up records of two replaced tables, a job and a pipeline for questions 56 and 57. The file is kept as committed, and no script rebuilds it |
| `test_technical_graph.py` | Tests: every term defined and cited, no layer list or owner property of its own, the example holding its committed figures and conforming, a negative test for each shape, and what 1.1.0 adds to 1.0.0 and keeps of it |

**Who answers for it (question 49)** follows a built object's design to its data product, the process that produces it, and that process's Accountable role in `organization`. In the ontology today no path reaches an owner: the pricing data products record no producing process, and the two data products that do are produced by processes with no RACI assignment.

**Status:** released as `1.1.0` on 2026-11-11, a minor release decided under the delegation of KPI-DEC-0001 (`../../domain/kpi-store-decisions/KPI-DEC-0001.md`); its changelog says why each term was added. `1.0.0` was released on 2026-11-02, which the subject matter expert approved (the decision of 2026-11-02, amendment of 2026-11-02, later). The package is in `../releases/technical-graph/1.1.0/`, and 1.0.0 is kept in `../releases/previous/technical-graph/1.0.0/`; it requires `data-product` 1.2.0, `kpi` 1.3.0 and `system` 1.5.0. The example graph stays test data outside the package. The stores load the package as they load every other package.

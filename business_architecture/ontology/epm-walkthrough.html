The business, and how it is mapped

This work began with a business problem. The downstream business had rebuilt its reports and lost track of what the numbers mean.

To say what a number means, you must first say which process produces it, in which value stream, and who answers for it. So the work starts from the business architecture, and the ontology comes later, as the checked form of that architecture.

The project's foundation document sets the chain below. Read forward, it is a design sequence. Read backward, it is an audit: take a number on a dashboard and trace it to a business goal someone owns.

"The Tableau-to-Power BI migration moved the pictures but not the meaning. Every report was rebuilt, but nobody recorded what each number means, who owns it, what good looks like, or where it comes from."

The project's foundation document, "Executive orientation" (not part of this release)

How a gap gets filled

Nobody edits the map to fix a gap on sight. A proposal states the gap, gives options and recommends one. The decision owner rules, and the ruling is recorded with their words. A change then changes the map, and a later core release carries the change, because each release builds from a pinned commit of the map.

What this does not do

Read this before you form expectations. The ontology defines the business; it does not run it.

The ontology

  • It calculates nothing. It defines what a measure means. Values stay in the business systems and in the tables that compute them.
  • It holds no records. Customers, invoices and transactions stay in their systems ("define, don't record").
  • It runs no process and replaces no system. It does not replace the ERP, a metric view or Genie.
  • The business has not signed it off. OPEN-ITEMS.md lists what the business still needs to answer, including who owns each concept's meaning.
  • It does not cover the whole company. Most enabling functions have no processes, and four areas are deferred.
  • Its IRIs do not resolve. They identify terms; nothing is hosted at those addresses.

The stores and the load

  • The stores do not keep themselves in step. A person runs the sync check, which says whether each store is current or behind. Keeping every store in step says what it reads.
  • Nothing corrects the ontology by itself. When the workspace and the ontology differ on structure, the load stops and writes a report. A person clears each row before a correction is cut.
  • The load changes no table but its own. It reads the catalogs the settings name and writes only to the KPI Store's two schemas.
  • A measure link proposed from a Genie space is a proposal. It is a report row for a person to confirm, and it does not stop the load.

The big picture and a reading order

One ontology describes the downstream business: its processes, who does them, the measures, systems, data products and market series. Everything else in the release either builds it, checks it, loads it into a store, or compares it with the platform.

The Turtle files in business_architecture/ontology/releases/ are the master copy. The Databricks table epm_triples, the Jena dataset and the Neo4j database are copies that can be rebuilt from them at any time (business_architecture/ontology/projection/pipeline.py, its docstring). The code in kpi_store/ loads the release into the client's platform and checks each load. Before the Databricks load it compares the ontology with the workspace, and it stops on a difference in structure.

How the ontology was built, from zero to done

It picked up from the process map and ended as 13 modules, each a versioned, checked release. The method came from a gated, twelve-step guide, and every choice that mattered was written down as a decision record.

The build can also be read as six stages, each one preparing the next: a controlled vocabulary, metadata standards, a taxonomy, a thesaurus, an ontology and a knowledge graph. The six stages are a way to read the build, and the method it followed is the twelve gated steps below. best-practices/README.md says why each stage comes where it does, which public standard it rests on, where this release holds it, and where the build's order differs.

The starting point

The source of truth is business_architecture/business_process/downstream_process_map.json: 680 nodes when the build started and 707 today, levels L0 to L6 (the first sections of this page describe the map). Beside it sit the value streams, the office lanes and the data-product portfolio (value_stream_*.json, office_lanes.json, data_product_portfolio.json) and their schemas in business_architecture/schema/.

The consistency reference is APQC's Process Classification Framework for Downstream Petroleum, v7.2.2: every local process is checked against it, and a deliberate divergence is recorded as a boundary note.

The end state it aimed for

"A standards-based ontology (RDF) published as a versioned DCAT catalog: a SKOS taxonomy of the process hierarchy, process definitions separated from executions, explicit RACI responsibility assignments, system and data-product linkages, SHACL validation shapes, and SPARQL regression tests derived from the competency questions." (the record of the original build)

And its non-goals: it defines what things are; it does not calculate KPIs, execute processes, or replace the ERP, the KPI store or Genie.

The standards it reused, and what it kept out

The build chose this stack: RDF (the grammar), SKOS (the taxonomy backbone), Dublin Core Terms (describing sources), RDFS/OWL (the schema layer, used sparingly), PROV-O (what happened and who vouches for it), the W3C ORG ontology (roles for RACI), SHACL (the checking layer) and DCAT (publishing).

You can see them in the release prefixes: organization uses org:, data-product uses prov: and dcat:, party uses foaf: and maps product values to the Open Energy Ontology (oeo:). No release uses owl:imports (core 2.4.0 has none).

Considered and kept out

the decision of 2026-10-05 found no public business-architecture ontology for downstream oil and gas. Upstream and plant ontologies (OSDU, O3PO, ISO 15926, IDO) did not fit. GLEIF Level 2, PIDX, the Open Energy Ontology, IOF Supply Chain and FIBO each cover a piece, so the ontology keeps its own terms and maps with skos:exactMatch and skos:closeMatch where they fit; IOF Supply Chain is parked. The worklog also set aside W3C SIOC and the ODPS family.

What the notebook does

The Databricks load is one notebook, kpi_store/notebook/kpi_store_load.py, run on serverless compute. It needs no token, because it uses the notebook's own session.

  1. It reads kpi_store.toml from the volume and checks the release zip beside it against the SHA-256 the settings name. A zip that differs stops the run.
  2. It reads the workspace (kpi_store/discovery.py), compares it with the ontology (kpi_store/compare.py), and writes discovery-report.json and discovery-report.csv to the volume.
  3. If a row of the report blocks, it stops there. Otherwise it loads epm_triples (kpi_store/load_databricks.py) and writes the marker row in epm_store_markers.

The notebook ends with a JSON summary whose status is blocked, checked, current, marked or loaded. Its mode parameter is load or check; check stops after the report.

The data-product package names 33 platform objects: 21 replica tables, 7 silver tables, 2 gold tables and 3 metric views, with 40 edges between them. The discovery reads what the workspace holds today, through the notebook's SQL session and a Genie client:

How the ontology gives Databricks objects their meaning

Unity Catalog knows that a metric view reads a table. It does not know what the number means, who uses it, or what it must not be mistaken for. The ontology holds that. This section walks one chain, from the measure KPI-0001, Crack Spreads Pricing, down to the replica tables, and says what carries each link.

One question, with and without the ontology

The question: "Is this crack spread our refining margin, and who relies on it?"

Without the ontology, Unity Catalog returns a metric view, its measure, and its lineage back to a table. The name suggests a margin, and nothing there says otherwise or names a user.

With the ontology, the answer is no. It is a benchmark, "Not realized refinery margin, not margin capture, and not MPC's R&M Margin Indicator". kpi names those three as measures not to confuse it with. The distribution, prompt and short-term planners use it, in process CM-1-1-4-7-4.

The chain, end to end

  1. The measure. kpi holds measure:crack-spreads, with the identifier KPI-0001 and the label Crack Spreads Pricing. Its definition is "Benchmark crack spreads: the market value of products made from a set ratio of crude, less the crude's price." Its scope note says "Not realized refinery margin, not margin capture, and not MPC's R&M Margin Indicator." It names what it is not to be confused with, and its grain, daily by market hub.
  2. What it links to. It informs the process CM-1-1-4-7-4, is used by the distribution, prompt and short-term planner personas, is the measure of series in market-data, and appears in two measure links in value-stream.
  3. The design. data-product names the metric view idp_sbx.semantic_sem_commercial.mpr_mips_crack_spread_price_fact_metrics_vw and says it serves the measure, through dp:servesMeasure. It reads the gold table idp_sbx.gold_commercial_core.mpr_mips_crack_spread_price_fact, which reads seven silver tables, which read replica tables in synapse_dev: replica_mips, replica_mpr and replica_kittyhawk.
  4. The comparison. Before each load, the comparison checks that every one of those objects, their named columns and the edges between them exist in the workspace under the names the settings give.
  5. The technical graph. The metric view as built gets a node, an IMPLEMENTS link to the measure and a DESIGNED_AS link to its design. READS_FROM follows the lineage the platform observed, down to the replica tables. A Genie space bound to the view gets a BINDS link.

The limits: what is not automatic

  • A measure link from a Genie space is a proposal. The comparison proposes it as a report row. A person who knows the space confirms it, and until then the ontology does not hold it.
  • Lineage appears only after a run. The platform records an edge when a job or a query runs. An object nothing has run since the lineage began gets a no-lineage row, which does not stop the load.
  • The platform keeps no name for every writer. A notebook or a query that wrote a table leaves no builder in the technical graph.
  • The technical graph is as old as its reading. It is rebuilt from a new discovery reading at each run. Between runs, the sync check compares each store's copy with the files of the last build, and it does not see a change in the workspace.

Keeping every store in step

The release's files hold the truth, and each store is a copy of them. The goal is that no store can fall behind without someone seeing it. Each store shows whether it is current, and a reload repairs it. Nothing runs the check by itself: a person runs it at the end of each load.

How to change the ontology

This release is your starting point, and your copy is yours to change. A released package never changes: a change is a decision by your owner, a new version and a new package. HOW-TO-UPDATE.md, in the release's top folder, has the worked commands for each change here.

Rules that apply to every change

  • Minor or major. Ask whether every query, report and answer made under the old meaning would still be correct. If yes, it is a patch or a minor. If no, or if unsure, it is a major (skills/ontology/references/release.md, rules 3 and 4).
  • Never delete a term. Mark it owl:deprecated, point to its successor, and do this only in a major (rule 5).
  • Who approves. Your ontology owner approves every major and every module's first release. A module owner approves that module's minors and patches.
  • Evidence. Cite the source of every fact you add, as the existing definitions do.

Add a logical model

A logical data model exported from ER Studio Data Architect joins the logical-model module as one more named model, not as a module of its own. The export stays exactly as ER Studio wrote it, and an annotation layer links each entity to its model, its source system, the party concept, class or code list it describes, and the data-product table or data product that builds it. These steps take one export from the email it arrived in to the release. The commands use the made-up example in logical-model/example/, so you can run them as written.

The guide's "Adding a logical model" says why the module is built this way. The method is the ontology skill's references/logical-model.md, and HOW-TO-UPDATE.md, "Add a logical model", has the release steps.

1. Clean the export

Skip this step for a file ER Studio wrote directly. An export that came through email or a word processor needs cleaning first, because a mail filter can rewrite IRIs into tracking links that still parse.

  1. Extract the Turtle from the document wrapper, such as an RTF file.
  2. Restore every rewritten IRI from the original target its tracking link encodes.
  3. Replace non-breaking spaces with plain ones and remove any heading the wrapper added. Leave every character inside a literal as written.
  4. Parse it. Check that every IRI is in ER Studio's namespace or a vocabulary you expect, and that the counts of classes and datatype properties match ER Studio's.
  5. Record each change, and keep the cleaned file beside the original.

2. Choose where the files live

A model is two files: ER Studio's export and a links file. Keep them in business_architecture/ontology/logical-model/models/, beside the module's sources, or in a folder of your own outside the release. HOW-TO-UPDATE.md, "Inputs from outside the repository", says what each way needs. Choose a slug for the model, such as example-logical-model, in lower case with words joined by hyphens.

3. Draft the links file

Write a CSV file beside the export with one row per entity. logical-model/example/example-links.csv is the pattern, and the module's README.md, "The links file", defines each column.

ColumnWhat goes in it
modelThe model's slug
erstudio_idThe entity's dcterms:identifier in the export
source_systemThe IRI of a system in system or a customer system in party, or none when neither holds it
describesThe IRI of a party concept, class or code list (a lookup table that holds a whole code list describes the list), or empty
implemented_byThe IRI of a data-product platform table or data product, or empty
statusasserted when the entity's name, description or ER Studio's metadata makes the links clear; otherwise doubtful
evidenceWhy the links hold, or why they are doubtful

4. Build the two graphs and verify them

The builder writes <slug>.erstudio.ttl, a byte copy of the export, and <slug>.layer.ttl, the annotation layer, into the export's folder. --verify fails unless both equal a fresh build. Try it on a copy of the made-up example, in a folder beside the release:

  --links ../../../../lm-try/example-links.csv --model example-logical-model --title "An example logical model" --write)
(cd business_architecture/ontology/logical-model && uv run -q --no-project --with rdflib python build_logical_model.py --export ../../../../lm-try/example-export.ttl \

For a real model, point --export and --links at its files and give its slug and title. To build two models together, repeat --export, --links, --model and --title once per model.

The build fails, and names the cause, when a row's identifier matches no entity, when an entity has no row, when a link target is not in the newest release of party, system or data-product, or when two models define the same IRI (a term both describe the same way, such as a reused attribute, is allowed; an entity never is). Fix a links-file failure in the links file, never by editing the export; a collision between two models comes from the exports themselves, so take it to the decision owner. The builder keeps each export byte for byte and renames nothing, so the build passes again only when the exports no longer share that IRI: one model is changed in ER Studio and exported again.

5. Settle the doubtful links with the decision owner

Only asserted rows become triples. Put every doubtful row, with its evidence, before the decision owner. Record each answer where you keep your decisions before you change the row's status, then build and verify again.

6. Get the release approved

The decision owner approves a model's first release from one page, which lists the doubtful links that remain; until then the module is a candidate. The owner approved logical-model 1.0.0 on 2026-11-02. A later model added to the module is a minor release. A re-export that drops or renames an entity removes an IRI, so apply the meaning-change test in "How to change the ontology" before you release it.

Glossary

KPI and OPM identifiers
Codes on measures in kpi 1.3.0. A KPI is a designation with a target and an owner (the decision of 2026-10-18); most measures are operational metrics, coded OPM.
Canonical fact
A node in core that carries an approved link between two processes and its evidence row.
Release package
A module's Turtle, JSON-LD, shapes, DCAT record, changelog and manifest, under releases/<module>/<version>/.
Projection
A copy of the releases in another store, rebuilt from the Turtle at will: epm_triples, the Jena dataset, the Neo4j database.
Discovery
One reading of the workspace: its objects, columns, metric views, lineage, builders and Genie spaces.
Discovery report
The rows the comparison of the ontology with the workspace writes. A row that blocks stops the load until a person clears it.
Correction version
A module version that the cut tool writes from a cleared report, marked in its version, as in 1.2.1-correction.1.
Metric view
A Unity Catalog view with dimensions and measures, queried with MEASURE().
Genie space
Databricks' question-answering agent over the tables it is bound to.
Technical graph
The record of what is built on the data platform in one environment, in the technical-graph module's terms.
Tech label
The label on the technical graph's nodes, never Resource, so the projection's counts stay put.
Marker
The record in a store of the release it holds, which the sync check reads.
PROV-O
W3C's provenance vocabulary; a run links to the process definition it followed through prov:hadPlan.

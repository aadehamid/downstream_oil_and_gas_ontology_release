What it is for

The ontology is one shared, checked vocabulary for how the downstream business works. It names the processes and how they relate, the roles that do them, what each measure means, which market series and data products carry the numbers, and which systems hold the data. A person, a report or an AI agent can then ask one question across all of it, such as "what does the crack spread mean, which view gives its value, and who works on the processes it informs?", and get an answer that cites its sources.

It holds definitions, never records. Actual customers, invoices and measure values stay in the business systems. The playbook's policy 2 calls this "define, don't record" (MODULES.md, "Three kinds of content").

The six stages of the build

The ontology was built in an order, and the order can be read as six stages. Each stage prepares the next one.

The six stages are a way to read the build. The method the build followed is the ontology skill's gated steps. best-practices/README.md gives the reasoning: why each stage comes where it does, what breaks if it is skipped, and where the build's order differs.

StageWhat it addsWhere this release holds it
1. Controlled vocabularyOne meaning for each term, with a preferred label, a definition and a stable ID.The skos:prefLabel and skos:definition of each term in the module files, and business_architecture/domain/business-glossary.md.
2. Metadata standardsA title, a version, a date and a source for each release and each term.Each package's Turtle header, catalog.ttl and manifest.json, in Dublin Core terms and DCAT.
3. TaxonomyA hierarchy with one parent for each term.The process hierarchy in core (skos:broader) and the concept schemes of the other modules.
4. ThesaurusAliases, matches to other vocabularies and related terms.skos:altLabel and skos:scopeNote, and the matches to outside vocabularies in party and data-product. The release has no skos:related link. This is the thinnest stage.
5. OntologyClasses, properties and rules.The thirteen modules, each package's shapes.ttl, and the competency questions with their regression.
6. Knowledge graphAll of it together, loaded and queried.The released packages, and the three stores that hold them: Databricks, Jena Fuseki and Neo4j.

Stages 1 and 3 rest on ANSI/NISO Z39.19-2005 (R2010), Guidelines for the Construction, Format, and Management of Monolingual Controlled Vocabularies. Stage 4 rests on ISO 25964-1:2011 and ISO 25964-2:2013, the standards for thesauri and for mapping between vocabularies. The other stages use the W3C standards in the card above: SKOS, Dublin Core terms and DCAT, OWL and SHACL, and RDF.

Why modules

The ontology could have been one large file. It is thirteen modules because each part has its own owner, its own sources and its own pace of change.

The ontology skill's playbook, "Why split an ontology into modules", gives the reasons, and the build followed each one:

  1. Each module releases on its own schedule. When item F changed the pricing measures, kpi went to 1.2.0 and core stayed at 2.3.0. Each module pins the versions it requires.
  2. Reviews and approvals stay small. A release changes one module or a few related ones: item F bundled five releases and item G three. The decision owner (the decision of 2026-10-12), approves each release plan (the decision of 2026-10-25, the decision of 2026-10-26). Who owns the meaning of each module is still open (competency question 17, the decision of 2026-10-23).
  3. Company facts sit apart from neutral ones. MPC's refineries and MPLX live in ref-mpc, so every other module could serve another refiner (the decision of 2026-10-05).
  4. Each module carries its own shapes and tests, and a whole-graph gate catches what breaks between them (the decision of 2026-10-19).
  5. Consumers load only what they need. A package's dependencies are read from the released manifests.
  6. A projection can tag every node with its module, so a walk across the graph shows where each fact came from.

Two rules keep the split sound. The module policy (the skill's foundations.md, policy 8) says modules depend one way, with no cycles, and use each other's terms by IRI, never by redefining them. A cycle would make a module impossible to release on its own.

Some splits follow the business's own lines. Market Data is a domain separate from commercial pricing, so its benchmark recipes have their own module (the decision of 2026-10-05). The cross-module rules (what certifies, which source wins, what an agent may answer) sit in one integration package above the rest.

The split has a cost. Each module pins the versions it requires, and a pin can lag behind a newer release of the module it names. That is why the closure rule, the whole-graph gate and each changelog's list of required versions exist. In this release every pin names the newest release.

The module map

core, the process map, is at the bottom. Most modules add one kind of thing and link it to core's processes. An arrow points from a module to a module it requires, as each release's manifest records. integration requires nine modules, every one except ref-mpc, technical-graph and logical-model; its arrows are dashed.

One measure, every module

Take one measure, Crack Spreads Pricing (measure:crack-spreads, identifier KPI-0001), and follow its links. Each module adds one piece of context, and together they answer what the number means, where it comes from, who works with it and what may be said about it.

The walk, as one query

This SPARQL query walks the measure's neighbourhood across seven modules: kpi, core, market-data, data-product, system, value-stream and organization. It runs over the thirteen newest releases loaded together, 37,233 triples since technical-graph 1.1.0. This command saves it as crack.rq, in the release's top folder:

cat > crack.rq <<'RQ'
PREFIX skos: <http://www.w3.org/2004/02/skos/core#>
PREFIX dcterms: <http://purl.org/dc/terms/>
PREFIX kpi: <https://w3id.org/mpc/ontology/modules/kpi/>
PREFIX mkt: <https://w3id.org/mpc/ontology/modules/market-data/>
PREFIX dp: <https://w3id.org/mpc/ontology/modules/data-product/>
PREFIX sys: <https://w3id.org/mpc/ontology/modules/system/>
PREFIX vs: <https://w3id.org/mpc/ontology/modules/value-stream/>
PREFIX orgm: <https://w3id.org/mpc/ontology/modules/organization/>
PREFIX measure: <https://w3id.org/mpc/ontology/modules/kpi/measure/>
SELECT ?hop ?label WHERE {
  { measure:crack-spreads kpi:measureKind/skos:prefLabel ?label . BIND("kind (kpi)" AS ?hop) }
  UNION { measure:crack-spreads kpi:informsProcess ?p . ?p skos:notation ?n ; skos:prefLabel ?l .
          BIND("informs process (core)" AS ?hop) BIND(CONCAT(?n, " ", ?l) AS ?label) }
  UNION { ?s mkt:seriesOf measure:crack-spreads ; mkt:region/skos:prefLabel ?r ; skos:prefLabel ?l .
          FILTER(?s = <https://w3id.org/mpc/ontology/modules/market-data/series/crack-gulf-coast-3-2-1>)

  UNION { ?v dp:servesMeasure measure:crack-spreads ; skos:prefLabel ?label .
          BIND("served by view (data-product)" AS ?hop) }
  UNION { ?v dp:servesMeasure measure:crack-spreads ; dp:dependsOnSystem/skos:prefLabel ?label .

  UNION { ?v dp:servesMeasure measure:crack-spreads ; dcterms:isPartOf/skos:prefLabel ?label .

  UNION { ?step vs:measureLink [ vs:measure measure:crack-spreads ; vs:relationship/skos:prefLabel ?rel ] ;
                skos:prefLabel ?l .
          ?stage vs:hasProcess ?step . ?stream vs:hasStage ?stage . ?stream skos:prefLabel ?sl .

}
ORDER BY ?hop ?label

Each module

Each module below says what it holds, why it exists, what it links to, and its part in the crack spread's story. The counts are from its newest release.

core 2.4.0 19,975 triples

Holds the process map: 463 processes, 23 capabilities and 2 structural anchors as a SKOS hierarchy under Downstream Operations and Enabling Functions. Each process has a notation (CM 1.1.4.7.4), a definition, a parent, and fields such as cadence, operating mode and business domain. It also holds 640 approved relationships between processes, such as core:informedBy and core:precedes, each as a direct triple and as a canonical-fact node that carries its evidence row. Since 2.4.0, no two processes share a name: the 25 that shared seven names take their parent's subject, such as Analyze Market Data, and keep the old name as history (MPC-P12, the decision of 2026-10-26).

Why: the process map is the authority every other module hangs on. It is built from business_architecture/business_process/downstream_process_map.json, and changes to the map go through proposals, never direct edits.

In the crack spread's story

The measure informs proc:CM-1-1-4-7-4, Capture Product/Crude/Feedstock Price, a monthly step of Refinery Optimization (CM 1.1.4.7), under Refining. Its definition: "Establish the price and economic assumption set used to value crude, feedstock, and finished-product streams in the optimization case". Six other price measures inform the same process.

Links: the other modules point at core's process IRIs (https://w3id.org/mpc/ontology/process/CM-…); core itself requires nothing. Open: 462 relationship mentions held for review, each re-judged only if its source is corrected (the decision of 2026-10-06, the decision of 2026-10-22).

kpi 1.3.0 1,190 triples

Holds 41 measure definitions, each classified by its kind: 15 operational metrics, 7 market indicators, 6 trackers or reports, 6 plan-variance diagnostics, 2 KPIs, 2 alerts, 1 decision-support indicator and 2 "not a measure". It also holds the four planning personas who use them. Eight measures carry their population, what they include and exclude, in MPC's own wording. Why: one meaning per measure, kept apart from any value, so that every report and agent uses the same definition (the decision of 2026-10-18, the decision of 2026-10-18, the decision of 2026-10-18). It is seeded from the planning team's measure list; filings are evidence for a definition, not a source of values (the decision of 2026-10-05).

In the crack spread's story

The definition lives here: measure:crack-spreads, "Crack Spreads Pricing", identifier KPI-0001, kind market indicator, grain "daily, by market hub", compared against a 30-day trend and 5-year history. It names three measures it is not to be confused with, such as margin capture. Its population excludes "the market cost of RINs, in MPC's 10-K regional and blended crack spreads".

Links: kpi:informsProcess to core. Requires core 2.3.0. Open: who owns each measure's meaning (competency question 17, business close-out point 1); the populations of the other 33 measures (point 10); Additional Market Prices names its renewables and NGL prices only as examples; and the crack spread's KPI ID has no silver source, being a constant from a legacy table (kpi 1.2.0 changelog, Known gaps).

market-data 1.1.0 1,403 triples

Holds the recipes of market series, never their prices: 15 benchmark series, their 28 legs over 24 benchmarks, refining and market regions, and 40 named market prices (mkt:MarketPrice) that the pricing measures present. Its shapes reject a price value.

Why: Market Data is a domain of its own, separate from commercial pricing, and owns benchmarks and their methodology (the decision of 2026-10-05). For the crack spread, MPC Economics' definition is the primary source, then MPC's filings, then peers, then exchanges (the decision of 2026-10-20).

In the crack spread's story

Fifteen series name the measure through mkt:seriesOf. The Gulf Coast 3-2-1 is three barrels of MEH crude producing two of USGC CBOB gasoline and one of USGC ULSD, in the Gulf Coast region. The region is MPC's Galveston Bay and Garyville refineries. A series enumeration records 127 series in 44 groups in the crack-spread view on 2026-10-25.

data-product 1.2.0 1,442 triples

Holds the data-product portfolio: segments, 19 product lines and 49 data products (16 defined so far). Why: a measure means something only if a consumer can find the data that gives its value. This module connects the business's data products to the platform objects that implement them (the decision of 2026-10-19, the decision of 2026-10-25).

Adding a logical model

A logical data model joins the ontology as two views of one model. The modelling tool's export stays exactly as the tool wrote it, and a small layer of annotations links each of its entities to the modules that already hold the systems, the party concepts and the platform tables. This section is the pattern for every logical model added from now on. The made-up example in logical-model/example/ shows it working, and the module's own README.md gives the detail.

What a logical model export is

A logical data model names the entities a business keeps data about, their attributes and keys, and how they relate, one level above the tables a data platform builds. ER Studio Data Architect, a relational modelling tool, exports one as Turtle. It writes each entity as an owl:Class and each attribute as an owl:DatatypeProperty, in its own namespace, https://www.erstudio.com/semanticmodel/, with a SHACL shape for each primary and alternate key. An entity's name says which source system its data comes from, and the system and party modules already hold those systems.

The two views

  • The tool's view. The export, kept byte for byte in its own file and its own named graph, with the tool's namespace, classes, properties and shapes. Nothing is re-minted, and no namespace rewrite touches it.
  • The annotation layer. Four annotation properties in the module's namespace, set on the tool's own entity IRIs: lm:inModel gives the model the entity belongs to, lm:sourceSystem the system its data comes from (a system of system, or a customer system of party), lm:describes the party concept, class or code list it holds data about (a lookup table that holds a whole code list describes the list), and lm:implementedBy the data-product platform table or data product that builds it.

The layer uses annotation properties because OWL gives annotations no logical meaning. A reasoner reads no axioms into the links, and the tool's classes stay plain classes.

In the made-up example

The example export holds three invented entities. Its links file asserts the links of two and marks the third doubtful. From those, the builder writes the layer. The account entity gets four links:

er:example_core_Example_Account_Dim

    lm:sourceSystem   system:profisee ;
    lm:describes      party:CustomerAccount ;
    lm:implementedBy  product:customer-master .

Here er: is ER Studio's namespace, system: the system module's systems, and product: the data-product module's data products.

The third entity, a region reference with no description, gets only lm:inModel until the decision owner settles its links.

Cleaning an export that passed through email or a word processor

The first export arrived inside an RTF document sent by email, and a mail filter had rewritten its namespace IRIs into tracking links (the decision of 2026-11-02, "Context"). A rewritten link still parses as an IRI, so a parse alone does not catch it. Before you use such an export:

  1. Extract the Turtle from the document wrapper.
  2. Restore every IRI the mail filter rewrote, from the original target the tracking link encodes.
  3. Replace non-breaking spaces with plain ones and remove any heading the wrapper added. Leave every character inside a literal as written.
  4. Parse the file, and check that every IRI is in ER Studio's namespace or a vocabulary you expect, and that the counts of classes and datatype properties match what ER Studio reports.
  5. Keep the cleaned file beside the original, outside the repository, and record each change. Ask for a direct export when one is possible.

Keeping every store in step

The release's files hold the truth, and each store is a copy of them. The goal is that no store can fall behind without someone seeing it. Each store shows whether it is current, and a reload repairs it. Nothing runs the check by itself: a person runs it at the end of each load.

The principles

PrincipleWhat it means
The release's files are the only place a change starts.Nobody edits a store to fix the ontology. A change is a new version of a module, as "How to change the ontology" says.
Data flows one way.From the files to the stores, never back.
Every store can be thrown away.Each can be emptied and loaded again from the files, so the repair for any drift is a reload.
A store proves itself before it is marked.sync_stores.py mark checks the Neo4j database against the release first and writes nothing when it does not match. The Databricks load writes its marker only after the table's hash equals the release files'.
Drift must be visible.A check that nobody runs protects nothing, so each load ends with the sync check, and a load is done only when every store reads current.

What to do, and when

The check says a store differsLoad that store again. Do not fix a store by hand

What the check does not catch

  • Nothing runs it on a schedule. A new version leaves the stores behind until someone loads them.
  • For the ontology in Neo4j and Jena, the check compares markers, graph names and counts. A hand edit that keeps every count would read as current. The load's own checks, which compare hashes, catch it at the next load.
  • A change in the workspace after the last discovery reading. The comparison at the next load finds it.

Neo4j: what is inside

Every name in the graph follows one rule. A property or relationship is prefix_name, such as skos_prefLabel or orgm_forProcess, and each node's IRI is in uri. Language-tagged text keeps its tag, so a label reads Crack Spreads Pricing@en.

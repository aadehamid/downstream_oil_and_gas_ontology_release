# Known open items

This page lists what is open in KPI Store 1.1, what has not run yet and what was left for later. Each item is yours to close or to leave in your own copy. `HOW-TO-UPDATE.md` says how to change anything here.

## What has not run yet

- **On Windows, a test job runs the checks and the runbook's chain, against a rehearsal Databricks workspace.** `.github/workflows/check.yml` runs `scripts/check.sh` under Git Bash on Windows Server 2025. Its job `stores` then runs the setup check with all 15 checks, the first run, the cleared report, the second run with the cut and every load, the sync check, the reset of the four stores, the load again, and the replace of an incomplete copy. The job signs in with a token that is a secret in the settings of the repository on GitHub; the release holds no token. Neo4j Desktop, Excel, the sign-in in a browser and the installs of the runbook do not run on Windows. The runbook's section "What ran where" lists each point.
- **Seven tests of the `ontology` skill do not run on Windows.** Four need a file mode or a missing Git that Windows cannot set up. Three test how `build_docs.py` swaps the Widoco pages in and restores them; they use a shell script in place of Java. So that swap is not proven on Windows. No step of the runbook or of `HOW-TO-UPDATE.md` builds those pages.
- **The reset runs in two tests, and never on the client's stores.** `py -m kpi_store.runner --reset` runs on macOS in the document test, against test servers and the rehearsal workspace, and the next run loads every store again. The Windows test job runs it too. Two parts differ on Windows: the stop of the Fuseki process, and the delete of its folder right after the stop. Windows frees a stopped program's files a moment later, so the reset tries the delete again for 10 seconds.
- **A few code blocks of the documents are run by no test.** `scripts/DOC-SNIPPETS.md` lists each one under "Blocks the test does not run", with the reason, what is done instead and who can run it. A test fails when a skipped block is missing from that list.
- **The first run on the client sandbox is still to do.** The owner does it from the zip, with the runbook.
- **The run on the owner's Windows machine is still to do.** The owner runs the setup check and then the whole chain against the sandbox, from the zip and the runbook.

## What was rehearsed, and what was not

- **The loop was rehearsed on a made-up workspace only.** On a Databricks workspace with made-up tables, the load stopped on one row, a person cleared it, the cut tool wrote `1.2.1-correction.1`, the load ran, and a second run changed nothing. The sync check's Databricks part ran there too. The client's workspace is the first real one.
- **Three kinds of discovery were not rehearsed there.** The rehearsal had no Genie space, so it produced no measure-link rows. It read no builders from jobs and pipelines. Databricks had recorded no lineage for the rehearsal's own tables, so the table edges were not compared with their lineage. The lineage queries ran against the real lineage of another catalog instead.
- **The copy to Neo4j Enterprise was not tested on a server without plugins.** It was tested against a second database on a server that has the plugins. A test that pins the exact statements, and the server's query log, show that the copy uses no plugin. The client's Enterprise server is the first target without them.
- **Question 1's `replaces` link is not proven on a composite database that holds the loaded technical graph.** The four questions passed on a Neo4j Enterprise composite database with a made-up graph. The technical graph that the loader builds was read with the questions' names on a single database only.

## Limits of this release

- **Measure links from Genie are proposed, not loaded.** The report proposes each link from a business measure to a view measure and its filter as a `measure-link` row, which does not block the load. Writing the links into the ontology waits for a minor version of the `data-product` module, with a new property for the filter.
- **The quality part of question 6 stays empty.** Nothing in this release records a quality check, so the `quality` column is an empty list until something does.
- **After a cut or a new version of a module, the documents' examples still show the release as shipped.** A version, a count or a refusal in an example may then differ from what the command prints. `scripts/check.sh` reads the examples, runs none of them, says so in a note and still passes. `scripts/DOC-SNIPPETS.md` says how to bring them up to date, under "The release the examples describe". An example that quotes a file is still compared with it. `kpi-intake/README.md` quotes the roles line of `for-the-architect.md`, so a release that changes the number of roles fails the check until that line is changed. "Change the RACI" in `HOW-TO-UPDATE.md` has the step.
- **After a cut, `projection-report.json` describes the earlier build.** The file changes only when a fresh Neo4j load is recorded. Until then `scripts/check.sh` prints a note and still passes.
- **The stand-alone check finds known forms of outside references only.** `scripts/check_standalone.py` looks for a list of patterns, with 40 exact exceptions in `scripts/standalone-exceptions.txt`. It cannot find a reference written in a form the list does not hold.
- **The check of a Cypher block in a document is a token check.** It finds a string, a backtick name or a bracket that is never closed, and not a misspelt keyword or clauses in the wrong order. `scripts/DOC-SNIPPETS.md` says more.
- **The changelogs do not all meet the ontology skill's Known gaps convention.** The skill's `check_changelogs.py` fails on some packaged changelogs, and `scripts/check.sh` does not run it. A released package never changes, so this waits for a later release of each module.
- **No command runs on a schedule.** A store is checked and reloaded only when a person runs the commands of `HOW-TO-UPDATE.md`.
- **The two viewers show the release as cut, not your later changes.** `viewer/index.html` and `horoi_viewer/index.html` each carry a copy of the ontology data. The second page is built with Horoi 0.2.0. Both were opened and clicked through in a browser by `business_architecture/ontology/viewer/browser_check.py`, which `scripts/check.sh` does not run because it needs a browser. Rebuild both pages after a cut; `viewer/README.md` gives the two commands.
- **The copy to Enterprise judges a node by its marks, not by who wrote it.** A node that another writer made with every mark of a KPI Store node counts as the KPI Store's, and a replace deletes it. Use a database that no other writer fills with ontology nodes of this shape. The runbook's section "The limits" lists the marks.
- **A logical-model node of a model that this release no longer holds stops the copy.** It no longer counts as the KPI Store's, so a person removes it before the copy goes on.
- **The reset leaves four things in place.** It empties the stores one after another and cannot undo a deletion, so a reset that fails part-way leaves the earlier stores empty; run it again. On Enterprise it drops nothing, so the constraint `n10s_unique_uri` stays. In Databricks it drops the four tables only, so a staging table that a killed load left behind stays. In a Neo4j database it judges a node by the marks of the release in this folder, so a node of a model or a class that this release no longer holds stays, as it does in a replace. A relationship from such a node, or from any node without the marks, to a KPI Store node makes the reset leave that whole database alone, and a person removes the relationship first.
- **The reset checks immediately before it deletes, and locks nothing.** Run it when nothing else writes to these stores. In a Neo4j database the check for another writer's relationship and the delete of a batch of nodes are in one transaction, but a relationship attached in the instant between the two is not caught and goes with its node. A part of the Fuseki folder's path that is changed to a link in the instant between the folder's check and its delete is not caught either.
- **The upload is two copies, not one step.** The runner copies the zip to the volume and then the settings. When the second copy fails, the volume holds the new zip beside the older settings, and the notebook refuses that zip by its checksum. Run the upload step again.
- **Two runner commands at once can submit two notebook runs.** The runner saves the Databricks run ID after the submit and waits for that run on the next command. Nothing locks the step, so a second command started at the same moment, or a command stopped between the submit and the save, can submit a second run. Run one command at a time.
- **The zip step's test for a password is by file kind and setting name.** It refuses a settings-like file (`.toml`, `.env`, `.ini`, `.cfg`, `.conf`, `.properties`) that gives a value to a setting named like a password, a secret or a token. A secret in another kind of file, or under another name, is not found. Keep every file with a secret outside the release folder.
- **The gate on SQL statements judges table names.** It refuses a statement that writes outside the two KPI Store schemas or reads a table outside the allowed catalogs and schemas. A read that names no table, such as a function that reads files, has no name to judge. Every statement comes from the release's own code, and none reads that way.
- **The report's check does not see a hand edit of a row's kind.** A row that blocks, rewritten as a kind that does not block, passes. Keep the report the notebook wrote and change only the decision columns.
- **A cut that is killed while it writes the release leaves it part written.** The backup is in a temporary folder that no message names. In a Git copy, `git status` shows what changed. In a plain folder, restore from your own copy.
- **A cut made from the report alone does not record its decisions file.** A second cut of the same run with other decisions is refused only when the first cut was given a decisions file. The runner always gives one.
- **The copy to Enterprise is not one transaction.** A copy that stops part-way leaves a database that the sync check reads as not current, and the next copy replaces it. `sync_check --quick` compares counts only, so use the full check after a copy that stopped.
- **A store that is already current still gets the technical graph.** When the ontology's copy in a Neo4j database is current, the load or the copy changes nothing of it and reports `current`, and it still replaces the technical graph's own nodes when they are behind. The printed line says so.
- **A marker row in Databricks is written in two statements.** A run stopped between the delete and the insert leaves no marker row. The sync check then reads the store as unmarked, and the next load writes the row again.
- **The input fingerprint depends on the line order of `inferred.nt`.** The same inferred triples in another order give another fingerprint, and every store then reads as behind. This shows only when the file's lines change order: after a hand edit, or after a projection run that writes them in another order.
- **The edge check of a subgraph load is a count.** `subgraph.py` compares the number of relationships made with the number sent. Two nodes with one uri, or a missing target beside a duplicate, could give the right count with the wrong edges. The technical graph's sync check reads the content back and would say so.
- **Four by-hand commands have narrower guards than the loads.** `sync_stores.py mark` marks a Neo4j database by its counts and release records, not by its content. `run_projection.py` started at a later step reads the files an earlier run left. `empty_stores.py` with no database in the settings empties the database you name. `load_verify.py` leaves an index that belongs to no constraint. The runner uses none of them this way.
- **Python may leave `__pycache__` folders in the release folder.** The commands that run in their own process do not, and the zip and the checks leave such folders out. In a plain folder they stay on disk. In a Git copy `git status` lists them as new files, because the release has no ignore rule for them. The cut does not count them as a change.
- **The questions' mapping file has four soft spots.** Its digest has no key, so a hand edit that also rewrites the digest reads as confirmed. `discover` writes over a mapping that was corrected and not yet confirmed. A path of exactly five steps is accepted and is not proposed. Question 7 returns no rows, with no reason given, when the mapping names a policy's link and neither its name nor a classification.

## The KPI intake pack

`kpi-intake/README.md` explains the pack. These points are not in this release.

- **A complete intake is applied by hand.** The check says whether a filled form is complete and signed, and changes nothing. The Architect adds the KPI with the steps of `HOW-TO-UPDATE.md`. Commands that propose the change from a form and apply it are planned for release 1.2.
- **The ontology has no place for a KPI's domain, and holds no list of domains.** The form asks for the domain and reads the list from `kpi-intake/settings.toml`, where the list that ships is an example to replace. The property the ontology names "business domain" holds the business area, which is the function that runs a process. A place for the domain is planned for release 1.2.
- **Sixteen more facts the form asks for, or a KPI has, have no property in the ontology.** Six are the business area of a measure, the decision it supports, its unit as a value of its own, the direction of a good value, who may see it, and its topic. Ten came with the questions that catalogue 1.1 added: the strategic objective, the grain, the status, the quality rule, the lifecycle, the thresholds and their effective dates, the named owner, the named steward, and an API or another access path. The form keeps the answers it collects in its own file. `kpi-intake/for-the-architect.md` lists each one, and item 6 of "Ontology updates to make on the target environment" below is the change that gives the ten a place.
- **Whether certification is an approval of its own is not decided.** Question 3.9 records the status the Data Owner has confirmed, and the form does not change it when someone signs. The organization decides whether "Certified" is a separate approval or the Data Owner's sign-off of the definition.
- **The form's lists differ from the ontology's in four places.** `kpi-intake/settings.toml` hides entries of four lists and adds two entries the ontology does not hold. The ontology is not changed. `kpi-intake/for-the-architect.md` lists what each list hides and adds. Items 1 to 5 below are the changes that make the ontology agree.
- **The kpi builder accepts only the four planning personas for "used by".** The form offers every role the ontology holds, and the check notes each chosen role that the builder cannot write yet.
- **One KPI may need releases of several modules.** The measure is a version of `kpi`. A value stream step, a new view and a new source document each need a version of `value-stream`, `data-product` or `integration`, and each release gives the modules that depend on it a new patch.
- **The check of names compares names, not meanings.** It finds a name that a measure or another module's term already has, and a name that is close in spelling. It cannot find the same measure under an unrelated name.
- **The HTML form was tested in Chrome only.** `kpi_store/intake/browser_check.py` opens it in an installed Chrome or Edge and proves twenty-one things. One statement of the guide `kpi-intake/how-to-use-the-form.html` was not tested: that a browser adds a number to the name of a download when the download folder already holds that name. `scripts/check.sh` does not run it, because it needs a browser. The workbook was read and written with `openpyxl` and has not been opened in Excel by a test.

## Ontology updates to make on the target environment

These changes to the ontology were left open on purpose. Make them on the target environment after the release is installed, with `HOW-TO-UPDATE.md`. They are also the first real test of that guide. Each item names the module it touches, why, and the section of the guide to follow. Every one ends with "The release steps". Where the tools of this release cannot make a change yet, the item says so.

1. **Add the role "Value Chain Optimization Director".** Module: `organization`. The business uses this role, and the form offers it from `kpi-intake/settings.toml`, marked as new. Follow "A new role or a new system" under "Add a concept or a property": the role is a row in `organization/roles.csv`, and its name a row in `organization/role-register.csv`. The build takes a role only when a RACI list of the process map names it. So the change starts with a proposal that names the role in the RACI of a process, and "Change the RACI" has those steps. It is a minor version. Then rebuild the form. Remove the role from `add` in `settings.toml` once no form in progress names it, as "Change the form" in `kpi-intake/README.md` says.
2. **Confirm whether "Black Oil Manager" is a real role, then deprecate it if it is not.** Module: `organization`. The form hides it until the business has answered. Follow "Deprecate a term". Its worked example is this role, with a made-up successor. A deprecation is a major version. The tools of this release deprecate a role into a successor only: a role that no other role replaces cannot be deprecated yet, and the section says what to do then.
3. **Add SharePoint as a system.** Module: `system`. The form offers it from `settings.toml`, marked as new, for question 7.4. Follow "A new role or a new system" under "Add a concept or a property": the system is a row in `system/other-systems.csv`, with its definition in `system/definitions.csv` and its source in `system/sources.csv`. It is a minor version. Then rebuild the form, and remove it from `add` in `settings.toml` once no form in progress names it.
4. **Class Databricks as the platform, not as a source system.** Module: `system`. The ontology lists Databricks among the systems, with the kind "application", so question 7.4 would offer it as a source of data. The form hides it. Follow "Change the kind of a term". Its worked example is this change, with a made-up definition of the new kind. The list of kinds has no value for a data platform, so the change adds one, and it is a major version. The form does not read a system's kind, so keep Databricks hidden in `settings.toml` after the change. The form also hides MS Excel, MS Outlook, MS PowerPoint and MS Teams as source systems. They stay in the ontology, where processes use them.
5. **Reclassify the 36 entries of the data-product catalog that are functional areas or portfolios.** Module: `data-product`. The catalog lists 49 entries, and 13 are data products. The form offers the 13 and hides the rest, such as HR, IT and Legal. Follow "Move catalog entries to another class". The catalog is built from the process authority's portfolio file, so the change starts with a proposal. The module has no class for a portfolio or a functional area, so the change also adds a class and changes the builder. Its worked example moves one entry. It is a major version.
6. **Give the form's new fields a place.** Module: `kpi`. Ten answers stay in the form's file today: the strategic objective of a measure that is not a KPI, the grain, the named owner and the named steward, the status, the quality rule, the lifecycle, the thresholds and their effective dates, and an API or another access path. Follow "Add a concept or a property", which covers a new property and the two places in `kpi/shapes.ttl`. Two need a decision first: the closed shape forbids a value on a measure, which a threshold is, and the ontology records roles and never a person's name.
7. **Add domains and their ownership.** Module: `kpi` for the list of domains, and a new module for their ownership. The first bullets of "The KPI intake pack" above say what is missing: the ontology has no domain concept, and the form uses an example list of eight domains from `kpi-intake/settings.toml`. Do this once the organization has named its domains. Follow "Add a controlled list to a module". Its worked example adds a made-up list of domains to `kpi`, with the property that points from a measure to its domain. It is a minor version. The domains with their owners are more than a list, and "Onboard another module" covers that part. The form cannot read a new list from the ontology in this release, so the domains stay in `settings.toml` too, under the same ids.
8. **Add the governance roles and their RACI.** Module: `organization`, or a new one. `settings.toml` holds the organization's seven governance roles with their definitions: Global Process Owner, Domain Owner, Data Owner, Data Product Owner, Data Steward, Digital IT and Enterprise Data Governance. The ontology's role register holds none of them under these names. It holds IT Data Owner, IT Data Steward and IT Data Custodian. The RACI of the seven is not in this release and must come from the organization. Follow "Change the RACI" for the roles and for their RACI on processes of the process map. It starts with a proposal to the process map. `organization` holds a RACI for those processes only, so a RACI for anything else needs "Change a process" or "Onboard another module" first. An assignment carries no date in this release. "Change the RACI" has a table that says which section covers which case. Where a governance role replaces a role of the register in every entry that names it, follow "Deprecate a term" and leave the old name in the process map. Add the governance role first, in the same release.

## Gaps in the ontology's content

These were found by reading the release against the six stages of `best-practices/README.md`. None stops a load. A released package never changes, so each one waits for a new version of its module, made with the steps of `HOW-TO-UPDATE.md`.

- **87 terms have a label and no definition.** 81 are in `data-product` (for example the product lines `finance`, `hr` and `it`), 3 in `core`, 2 in `system` and 1 in `party`. Each definition must come from the business or from a source, so none was written for this release. Fix first: a patch release of `data-product`, then of the other three.
- **The taxonomy check does not run on the released modules.** `scripts/check.sh` runs the tests of `skills/ontology/scripts/check_taxonomy.py`, and never the script on a package. Run by hand with no options on the newest package of each module, it reports the 87 missing definitions and these other findings: text with no language tag (1,130 in `core`, 940 in `organization`, 275 in `kpi`, 110 in `market-data`, 91 in `party`, 65 in `data-product`, 13 in `value-stream`, 7 in `ref-mpc`), 56 notation findings in `core`, 23 domain or range findings across seven modules, 19 untyped terms in `integration` and `lane`, and 11 property-kind findings in `ref-mpc`. Some of these may be accepted with the script's options; no one has sorted them for this release. Fix second: sort the findings, release what needs a change, then add the script to `scripts/check.sh` so the gaps cannot return.
- **Only `core` states its rights.** `dcterms:rights` is in the `core` package and in no other. The owner decides what the statement says; it then goes into the next release of each module.
- **The thesaurus stage is thin.** Eight modules give terms an alternative label. No term has a `skos:related` link. Only `party` and `data-product` link to an outside vocabulary, and the release has no mapping file of its own. Add these when a reader or a tool needs them.
- **The build did not follow the six stages in every place.** The process hierarchy came before the definitions, and each package's metadata was written at release, after the ontology. `best-practices/README.md`, "Where the order differs", lists each place.
